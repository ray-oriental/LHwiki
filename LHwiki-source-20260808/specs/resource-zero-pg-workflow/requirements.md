# LHwiki 普通工作流零 PostgreSQL：第二阶段需求

状态：已由用户确认（2026-09-09）；设计与任务清单均已确认，实施中

## 1. 背景与约束

- 2026-09-09 的账单与 CLS 对齐结果显示：一次约 5 分钟内的外部 PostgreSQL 读取簇之后，当小时最终记账为 900 核秒、85.5 资源点。官方规则说明共享实例按实际使用的 5 分钟区间计量，但没有说明固定 30 分钟最低消费；因此“约 30 分钟尾部”只作为本环境的保守实测成本，不把平台内部原因写成已证实事实。
- 2026-09-09 13:05 左右曾核对到约 829 点，但用户随后按控制台最新观感把当前周期预算基线保守上调为约 1000 点；后续设计统一按“只剩约 2000 点绝对余量”计算，不把早先快照当作当前值。为了称得上轻松运营，本周期仍以最终不超过 2100 点为目标，即从约 1000 点基线起正常运营和本次切换合计再用不超过约 1100 点，并保留约 900 点相对硬上限的安全余量。旧的“每个唤醒桶约 14.25 点”假设已经失效。
- v0.8.9 已让公开首页、公开文章、普通登录、会话恢复和本机自动恢复不访问 PostgreSQL；当前安静区间也未观察到持续 PostgreSQL 访问。
- 剩余风险来自手动保存、投稿、审核、发布、权限管理和备份等显式动作。即使每个动作只访问一次 PostgreSQL，只要每次孤立访问都可能产生约 85.5 点，也不足以保证 3000 点内轻松运营。

## 2. 目标

1. 普通用户与审核者的日常完整流程同步访问 PostgreSQL 的次数为 0，包括：云端手动保存、删除草稿、投稿、退回修改、审核、发布、教师补充和查看个人/审核列表。
2. PostgreSQL 仅作为低频归档、灾备或人工维护目标，不再是网站正常请求的在线依赖。
3. 网站现有页面、操作入口、响应速度、内容结构、审核规则和公开阅读体验保持不变；不得用关闭投稿、减少审核能力或让用户等待批处理完成来节省资源。
4. 本周期总消耗绝不超过 3000 点、正常目标不超过 2100 点；“约 2000 点余量”仅是从当前起的红线，不是允许全部花完的目标。切换完成后，计划性 PostgreSQL 激活原则上每周不超过 1 次，且不得存在每日后台唤醒。

## 3. 功能需求与验收标准

### R1. 端侧写作与显式同步

1. 输入过程只写本机 `localStorage` 或 `IndexedDB`，不得因按键、停顿、联网、页面隐藏、关闭页面或失败重试而访问云端。
2. 用户点击“立即保存”时仍应在一次前端请求内完成持久化，并在成功后立即显示已保存状态。
3. Cookie 只用于必要的会话或安全标识，不得存放正文、投稿内容、审核记录等大体积或敏感数据。
4. 断网时编辑不受影响；恢复网络后由用户显式保存。失败不得清除本机副本，也不得无限自动重试。

### R2. 非 PostgreSQL 在线工作流

1. 草稿、投稿、教师补充、审核事件、用户权限和发布状态必须有一个持久、可备份、非 PostgreSQL 的在线权威存储。
2. 必须兼容附录 A 中列出的现有 API 路径、请求业务字段、成功响应主要字段以及 400/401/403/404/409/429 错误语义；新增幂等请求头和客户端升级错误属于允许的协议扩展。
3. 一次保存、投稿或审核动作不得拆成需要用户等待的异步批处理。普通读取在服务端收到请求后 800ms 内完成、普通写入在 2s 内完成，作为预发布环境连续 20 次请求的 P95 目标；超过 8s 必须按失败处理，不得让界面无限显示“保存中”。
4. 写入成功响应返回时，新状态必须能够被随后一次本人或审核者读取立即看到。超时或失败时，界面保留本机副本、明确显示未保存并允许用户以同一幂等键手动重试。
5. 审核通过或管理员发布时，公开快照必须从新的在线权威存储生成，不得沿用“回读 PostgreSQL 后生成”的路径；成功响应返回时公开快照已经写入，失败则返回可重试错误，不能谎报发布成功。
6. 普通读者继续只读取公开快照，不依赖私有工作流存储或 PostgreSQL。
7. 正常函数入口不得静态导入、动态导入或实例化 `pg-store.cjs`，且不得读取 `PG_ARCHIVE_*` 等维护专用配置。新在线存储/公开快照使用的 `WORKFLOW_STORE_*`、`PUBLIC_SNAPSHOT_*` 配置必须与归档配置分名管理；若平台只能提供同一环境级凭据，也不得在正常函数包中保留可到达的 PostgreSQL 请求代码。
8. 生产式装配验收分两层：本地使用共享 fake 新存储跑完整业务契约，并用模块加载钩子证明 `pg-store.cjs` 从未加载、用网络拦截证明 `/v1/rdb/rest/` 从未请求；预发布使用真实候选存储重复同一套契约。只有独立的归档、迁移、恢复或人工维护入口可以加载 PostgreSQL 客户端。

### R2A. 国内访问与网址保持

1. 现有 CloudBase 主站网址和备用网址必须保持不变，不更换域名、不要求用户更新收藏，也不把浏览器重定向到 `workers.dev`、Cloudflare API 或其他境外服务。
2. 浏览器继续只请求当前站点的同源 `/api/*` 与静态资源；不得因存储改造新增跨域登录、第三方 Cookie、CORS 白名单或前端可见的存储域名。
3. 普通请求的用户路径保持“国内浏览器 → CloudBase 上海静态托管/HTTP 函数 → 腾讯云内资源”。任何境外服务只能作为离线灾备，不得成为首页、阅读、登录、保存、投稿、审核或发布的在线依赖。
4. 部署验收必须分别从中国大陆网络验证现有主站和备用站：首页、文章读取、登录、手动保存、投稿与审核路径均可用，且浏览器地址栏与 API origin 未改变。

### R3. 数据隔离与安全

1. 私有正文、学号、权限和审核记录不得出现在公开快照、公开对象路径、无需签名即可访问的 URL 或浏览器可枚举的全局索引中。
2. 普通用户只能读取和修改自己的草稿与可编辑投稿；审核者和管理员沿用现有最小权限边界。
3. 用户权限必须以新的非 PostgreSQL 私有权威记录为准。每次特权操作都应校验该记录；缓存按用户 ID 与权限 revision 标识，TTL 不得超过 60 秒，角色修改应主动使处理该修改的实例缓存失效。
4. 权限测试必须创建两个相互独立、各自持有缓存的应用实例，连接同一 fake 权限存储并共享可控时钟：先让两实例缓存旧角色，再由实例 A 撤销权限；A 的下一次操作应立即拒绝，时钟推进 65 秒后实例 B 必须拒绝。预发布再用两个冷启动函数实例验证同一上限。
5. 所有写操作继续执行现有来源校验、CSRF、签名会话、内容体积限制、内容净化和速率限制，并新增 R4 定义的幂等/重放防护；不得把尚不存在的独立 nonce 机制误称为现有能力。
6. 新存储方案必须先验证生产桶/资源的私有性和服务端访问边界；若无法证明，不得存放真实私有内容。

### R4. 一致性、并发与幂等

1. 草稿继续使用 revision 乐观锁；两个客户端以同一 revision 保存时，只能一个成功，另一个返回 409，不得静默覆盖。
2. 网站客户端对投稿、草稿提交、审核、发布、教师补充和权限变更必须发送 `Idempotency-Key` 请求头。键按“操作者 + HTTP 方法 + 路径”隔离，至少保存 30 天；相同键和相同规范化请求体重试时返回第一次完成后的相同业务结果，不得重复写入；相同键配不同请求体返回 409。
3. 需要幂等键但由旧客户端漏传时，服务端必须在访问权威存储前返回 HTTP 409，响应至少包含 `{ error: <中文说明>, upgradeRequired: true }`；读取接口及其响应保持兼容。
4. 草稿、投稿、教师补充、权限和审核状态转换都必须使用条件版本或等价的原子条件。两个审核者并发处理同一记录时只能一个完成，另一个收到 409；不得重复发布或覆盖新状态。
5. 投稿成功之前不得删除草稿。提交/审核/发布的“准备中、业务记录已提交、公开快照待确认、已完成、可重试失败”是权威存储内持久化的内部操作日志状态，现有业务 API 不直接暴露这些新状态。
6. 现有读取 API 只能看到最后一个已完成状态：投稿提交未完成时仍显示原草稿；审核/发布未完成时仍显示原投稿状态，且新文章不得进入公开快照。相同幂等键重试从操作日志记录的未完成步骤继续。
7. 本需求所称派生索引仅包括个人草稿/投稿列表、按状态审核队列、权限查询清单和公开快照。每个公开快照必须携带对应权威事件末端 ID、版本与内容哈希；全部所需索引可读、其末端 ID 一致且快照哈希匹配时，操作才可标记完成并返回成功。
8. 审核队列、个人列表和公开快照必须可从权威记录重新构建，不能把一个容易竞争覆盖的共享索引作为唯一真相。
9. 每条业务变化必须记录实体 ID、经授权的操作者标识、动作、前后状态与 revision、内容哈希和时间。审计事件不得复制正文、会话密钥或其他不必要敏感内容。

### R5. 归档、备份与恢复

1. 新权威存储及其独立备份是正常恢复来源；PostgreSQL 只可作为可选的第二审计/冷归档副本，不得成为唯一备份，也不得成为读取新业务状态的前提。
2. PostgreSQL 归档默认关闭。若启用，必须把一批变化集中在一个明确维护窗口内，频率最多每周一次；没有待归档事件时在本地/对象存储侧直接退出，不得先访问 PostgreSQL 判断。
3. 每个归档批次必须有稳定批次 ID、连续源事件范围、数量和内容哈希。只有目标写入完成并回读验证数量与哈希后，才能原子推进包含“最后已确认事件”的检查点；失败不得推进，重试同一批次不得生成重复记录。
4. 新权威存储必须纳入独立备份与恢复测试。成本基准固定为每月 10,000 次私有读取、2,000 次草稿保存、500 次投稿/重投、500 次审核/权限写入、100,000 次公开快照读取、1,000 次快照写入、10,000 条私有记录、1GB 私有数据和 10 次完整备份。设计必须引用当日官方单价逐项估算；新增非 PostgreSQL 资源的月度预测不得超过 200 资源点，若是外部付费服务则不得超过 200 资源点折算金额且须另行征得授权。
5. 生产切换前必须在隔离环境完成一次恢复演练：用不可逆替代值处理真实学号和正文，但保留用户间归属关系、角色、revision、状态转换和幂等键结构；恢复后须通过跨用户隔离、并发保存、重复审核、列表重建和公开快照哈希验证。

### R6. 迁移与回滚

1. 迁移期间必须完整保留 PostgreSQL 原数据，不修改或删除已应用迁移文件。迁移范围必须覆盖全部历史与当前的用户权限、栏目、文章、贡献者、草稿、投稿、审核事件、教师补充、教师索引以及仍有业务意义的关联状态；不得只迁移已发布文章或当前待审数据。
2. 切换应支持“历史数据从 PostgreSQL 只读、新写入进入新存储”的受控过渡，或提供等价的可验证方案；不得要求一次不可逆停机迁移。
3. 必须有配置级回滚开关，但只有在新存储事件已全部回放/合并到回滚目标，并通过记录数、末端事件 ID、状态和内容哈希校验后才算回滚完成；仅切换配置不算成功，且不得丢失切换后新产生的数据。
4. 创建云资源、迁移真实数据、修改生产权限或部署均需单独授权；需求、设计和本地实现阶段不得隐式执行。
5. 正式切换前必须对每类记录生成迁移清单，逐项核对源/目标记录数、稳定主键、外键关系、状态、revision、时间戳和规范化内容 SHA-256；任何差异、孤儿记录或无法解密记录都会阻止切换。切换完成后 PostgreSQL 至少保持只读原状一个完整计费周期，直到恢复演练通过且用户另行授权清理。

## 4. 资源预算验收

1. 自动测试证明所有公开读取、普通登录、手动保存、投稿、审核、发布和列表读取均为 0 次 PostgreSQL 调用。
2. 预发布环境至少完成：两位普通用户同 revision 并发保存、重复投稿、两名审核者并发处理、审核退回后重投、审核通过、教师补充、角色授予与撤销、快照写入故障、超时重试和恢复演练。
3. 生产切换后观察至少 24 小时。窗口内至少核验 10 次私有读取、5 次手动保存，以及一组“投稿 → 退回修改 → 重投 → 通过”的受控流程；这些事件均要用请求时间/操作 ID 与 CLS 对齐，其对应的 PostgreSQL 外部访问桶必须为 0。受控数据必须与真实内容隔离且可审计清理。
4. 若执行周归档，一个自然周内只允许一个有证据归因的 PostgreSQL 激活事件；监控以实际账单增量为准，不用固定 14.25 点估算。
5. 切换后健康目标为不超过 10 点/日，超过 20 点/日告警；达到 40 点/日或按当前累计值与剩余天数预测周期末超过 2100 点时，停止非必要维护并排查。若从本需求基线起新增消耗接近 2000 点，或预测周期末接近 3000 点，则进入硬性停机保护边界。

## 5. 非目标

- 不改变网站视觉、编辑器交互设计、栏目体系、投稿规则或人工审核职责。
- 不恢复云端自动保存，不引入多人实时协作。
- 不把纯端侧缓存当成多人共享工作流的唯一存储。
- 不为减少点数而降低鉴权、隐私、审计、数据完整性或恢复能力。
- 本阶段不预先指定一定使用旧 COS、PG Storage、NoSQL、Cloudflare D1 或其他产品；技术设计必须用安全性、一致性、维护成本、资源消耗和回滚能力比较后再选型。

## 6. 需求确认后再决定的问题

1. 权威在线存储选择：现有旧 COS 的私有对象事件流、新建请求计费型存储、复用灾备 D1，或其他不按空闲 CPU 计费的方案。
2. 如何实现条件写入、每用户/每状态查询和权限清单，而不引入共享索引竞争。
3. 是否需要 PostgreSQL 周归档；若对象存储本身的版本、备份和恢复已足够，可进一步改为仅人工归档。
4. 切换采用双读、双写还是事件回放，以及每种方案对应的最小生产变更和回滚路径。

## 附录 A：必须保持的 API 契约

### 读取

- `GET /api/mine`
- `GET /api/drafts/mine`
- `GET /api/submissions/mine`
- `GET /api/teacher-submissions/mine`
- `GET /api/review?status=...`
- `GET /api/admin/users`

### 写入

- `POST /api/drafts`
- `PUT /api/drafts/:id`
- `DELETE /api/drafts/:id`
- `POST /api/drafts/:id/submit`
- `POST /api/submissions`
- `PUT /api/submissions/:id`
- `POST /api/teacher-submissions`
- `POST /api/review/:id`
- `POST /api/review/teachers/:id`
- `PUT /api/admin/articles/:slug`
- `DELETE /api/admin/articles/:slug`
- `POST /api/admin/roles`

兼容判定：实施前把现有集成测试中的请求体、主要成功字段和错误状态码固化为契约夹具；新实现逐项复用这些夹具。除新增 `Idempotency-Key`、明确的旧客户端升级错误和内部不可见元数据外，不得要求前端改变现有业务字段或页面流程。
