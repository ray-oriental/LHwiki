# LHwiki 普通工作流零 PostgreSQL：技术设计

状态：已由用户确认并于 2026-09-09 上线；等待 24 小时资源账单观察完成

## 0. 已上线实现与原设计修正

Phase 0 发现原公开快照桶已开启版本控制；腾讯云的 `x-cos-forbid-overwrite` 在该状态下不能提供条件创建。因此下面早期设计中的“同桶 reservation/commit 多对象协议”没有上线。最终实现为：

1. 新建上海地域专用私有桶 `lhwiki-workflow-20260909-1465088461`，保持版本控制关闭，并用真实函数身份验证同一路径首次创建成功、第二次写入返回冲突。
2. 私有状态以加密复合事件推进。每个事务用当前事件集合的稳定指纹生成唯一的下一代 HMAC 路径，并以 `x-cos-forbid-overwrite: true` 条件创建；同一代并发写只能有一个成功，失败方重新载入最新状态并重新执行状态机，最多重试五次。
3. 64KB 以上正文分块压缩并使用 AES-256-GCM 加密，块路径为服务端 HMAC；对象路径和公开快照不含学号、正文或审核私有字段。
4. 所有业务写要求前端持久化 `Idempotency-Key`。事件保存规范化正文哈希和首次业务结果；网络结果不明时，同键同体重放原结果，同键异体返回 409。
5. 审核发布后写入 `generation + 内容哈希` 命名的不可变公开快照；固定 CDN 对象只是兼容别名，不是权威指针。快照失败时请求返回 503，并保留待补偿标记；同一幂等键重试先补齐快照再返回原结果，不重复审核。
6. 正常 `lhwiki-api` 部署包不包含 `pg-store.cjs`、迁移文件或 PostgreSQL API Key；公开快照仍使用原 COS/CDN，私有工作流使用专用桶。原 PostgreSQL 与加密迁移前备份均保留且不再由正常请求访问。

本节是当前实现的权威说明；下文中出现的 reservation、独立 commit 和 checkpoint 描述保留为设计过程记录，不代表已部署对象布局。

## 1. 结论

正常线上链路保持在腾讯云上海地域，现有两个网站入口和全部同源 `/api/*` 路径不变：

- 主站：`https://lhwiki-d9g6r8vfzc7be1c0a-1465088461.ap-shanghai.app.tcloudbase.com/`
- 备用站：`https://lhwiki-lhwiki-d9g6r8vfzc7be1c0a.webapps.tcloudbase.com/`

浏览器仍只访问上述 CloudBase 静态托管和 `lhwiki-api` HTTP 函数。函数内部把正常工作流的权威存储从 PostgreSQL 换成上海地域的专用私有 COS 桶：业务变化以全局逐代条件创建的加密事件提交，列表由确定性事件重放得到，公开内容来自不可变版本快照与缓存。PostgreSQL 不再被正常函数包导入或访问，只保留为切换前历史副本及独立维护入口的可选冷归档目标。

该设计不改变页面、编辑器交互、栏目、审核规则、用户网址或公开内容结构，也不把 Cloudflare、`workers.dev`、境外数据库或第三方 Cookie 放入国内用户链路。

## 2. 选型

### 2.1 采用：腾讯云私有对象事件存储

选择原因：

1. 云存储按容量和请求计费，不存在 PostgreSQL 被一次孤立访问后继续累计核时的问题。
2. 存储与函数都在腾讯云上海地域，浏览器地址和同源 API 完全不变。
3. COS `PUT Object` 支持 `x-cos-forbid-overwrite: true`；在未开启版本控制的桶中，同名对象已存在时可拒绝覆盖。因此可用确定性对象键实现幂等占位和乐观锁，而不是依靠容易被覆盖的共享 JSON 文件。
4. CRC64、内容哈希和私有 ACL 可以分别覆盖传输完整性、业务完整性和访问边界。
5. 现有环境已经使用云存储保存公开快照，可在不引入新用户端依赖的情况下复用同一区域能力。

正式实现以第 11 节“Phase 0 能力验证”通过为前提。未验证当前 CloudBase 上传授权链确实接受防覆盖头、读写后可及时列举、生产桶为私有且未开启版本控制前，绝不迁入真实私有数据。

### 2.2 不采用：Cloudflare D1 作为在线权威存储

D1 的请求式计费、事务批处理和顺序一致会让实现更简单，但项目历史已验证直接 Cloudflare 链路在中国大陆不够稳定。即使浏览器不直接访问 D1，CloudBase 上海函数到境外服务仍会把保存、投稿和审核变成跨境在线依赖，不满足国内可访问性硬约束。D1 仅保留为离线灾备候选，不参与正常请求。

### 2.3 不采用：另建 CloudBase 文档数据库环境

当前 PostgreSQL 型环境不能同时使用文档型数据库。另建上海云数据库环境虽然能保持前端网址，但文档数据库按 40 点/GB/天计费，1GB 基准仅容量约 1200 点/月，尚未计算调用，无法满足新增存储不超过 200 点的预算。

### 2.4 不采用：正文放 Cookie

Cookie 只保留会话和安全标识。正文、草稿和审核数据放入 Cookie 会受约 4KB 限制，并在每次 HTTP 请求中重复发送，既不安全也浪费流量。编辑过程继续使用本机 IndexedDB/localStorage；用户显式保存后才写在线对象存储。

## 3. 总体结构

```text
中国大陆浏览器
  ├─ 本机 IndexedDB/localStorage：输入过程、断网副本
  └─ 原 CloudBase 同源 /api/*：显式保存、投稿、审核、发布
       └─ lhwiki-api（上海）
            ├─ WorkflowService：鉴权、状态机、幂等、乐观锁
            ├─ CosWorkflowStore：私有不可变事件/提交/检查点
            ├─ PublicSnapshotStore：仅公开字段的版本化快照
            └─ 进程内只读缓存：按检查点末端 ID 失效

独立维护面（不在正常函数包内）
  ├─ PostgreSQL 只读迁移器/可选周归档器
  ├─ 加密本地备份与恢复工具
  └─ 数据清单、哈希与恢复演练
```

正常函数入口不得包含可到达的 PostgreSQL 代码或 `PG_ARCHIVE_*` 配置。迁移、归档和恢复使用独立脚本/独立函数包，默认不部署、不定时运行。

## 4. 数据模型与对象布局

所有私有对象位于专用私有前缀，路径只含随机或 HMAC 后的标识，不出现学号、姓名、文章标题或正文片段。示意布局：

```text
private/workflow/v1/
  reservations/<scope>/<entity-hmac>/<revision>/<attempt>.json
  reservation-aborts/<scope>/<entity-hmac>/<revision>/<attempt>.json
  blobs/<hmac-of-content-hash>.chunk.gz.enc
  operations/<operation-hmac>/event.json.enc
  operations/<operation-hmac>/commit.json
  checkpoints/<generation>-<sha256>.json.gz.enc
  checkpoint-commits/<generation>-<sha256>.json
  migration/<migration-id>/manifest.json.enc

public/workflow/v1/
  snapshots/<generation>-<sha256>.json.gz
  snapshot-commits/<generation>-<sha256>.json
```

每个逻辑操作只产生一条复合事件。正文先按固定上限分块、压缩并加密，使用带服务端密钥的内容哈希作为不可枚举对象键；已有块直接复用，事件只引用有序 blob 清单、总长度与全文哈希。这样长文多次手动保存只新增变化的块，不会为每个 revision 重复保存整篇正文。相同块的并发首次写入仍使用禁止覆盖，胜者写入后其余请求回读并校验后复用。

事件可以同时描述草稿状态变化、投稿创建、审核状态变化、文章发布和审计摘要，避免依赖跨多个对象的事务。事件在对应 `commit.json` 成功创建前不可见；读取模型只折叠“正文块齐全且哈希匹配、事件存在、提交标记存在”的操作。

权威事件覆盖现有全部业务类型：用户与角色、栏目、文章、贡献者、草稿、投稿、教师投稿/补充、审核事件、发布状态、幂等结果和必要审计信息。检查点包含这些事件折叠后的完整状态以及可重建的个人列表、审核队列、权限索引和公开快照索引。

## 5. 一致性、并发和幂等

### 5.1 请求标识

所有业务写请求要求 `Idempotency-Key`。服务端计算：

`operationId = HMAC(keyId, actorId + method + path + idempotencyKey)`

事件内保存规范化请求体 SHA-256。相同 operationId 与相同请求哈希返回第一次的业务结果；相同 operationId 配不同请求哈希返回 409。浏览器仅保存自己的随机幂等键，不接触服务端 HMAC 密钥。

幂等记录至少保留 30 天；只要相关业务实体仍存在，其最终结果摘要可继续保留。旧客户端漏传幂等键时，服务端必须在读取权威存储前返回 HTTP 409 与 `upgradeRequired: true`。

### 5.2 乐观锁

对草稿、投稿、审核对象、文章和用户权限分别创建确定性的 reservation 对象，键中包含实体 HMAC、期望 revision 和下一 revision，并要求禁止覆盖：

- 第一个创建成功的请求获得该 revision 的唯一写入权；
- 同 revision 的并发请求因对象已存在返回 409；
- reservation 指向 operationId，重试同一 operationId 可继续未完成步骤；
- reservation、事件和提交对象均不可原地覆盖。

发布或审核这类多实体变化把全部前置 revision 写入同一个复合事件，并按 scope 与实体键的固定字典序取得 reservation，避免相反顺序的争抢。公开快照另有全局 `public-snapshot` revision reservation，两个并发发布不能各自覆盖对方的快照。若任一 reservation 失败，操作不提交，读取仍看到旧状态。

reservation 不能让一次断网永久锁死实体：若新请求发现该 revision 已被占用，会读取其指向的 operation。操作者与规范化请求哈希相同则直接接续原操作，即使浏览器丢失了旧幂等键也不会重复写；已经 commit 则返回原结果。若多实体操作只取得部分 reservation 就发生确定性冲突，服务端为该 attempt 写不可变 abort 标记，已取得项随之失效。超时且结果未知的 attempt 不自动抢占；由恢复器确认不存在 commit、事件/快照状态可判定后写 abort，再以递增 attempt 竞争。abort 与 takeover 全程留痕，不物理删除旧对象。

### 5.3 提交顺序

一次写入按以下顺序进行：

1. 校验会话、CSRF、来源、权限、体积和速率限制；缺少幂等键则在访问存储前返回升级错误。
2. 读取当前已提交状态并校验业务状态机与 expected revision。
3. 为受影响实体创建不可覆盖 reservation。
4. 写入加密复合事件并回读验证 CRC64/长度/SHA-256。
5. 构建受影响的派生索引；若为发布操作，同时写入新的版本化公开快照并验证哈希。
6. 最后创建不可覆盖的 commit 对象。只有此步成功后新状态才可见。
7. 返回结果并更新当前函数实例缓存。任一步超时均返回未保存；同一幂等键重试从已有对象继续，不重复业务变化。

持久内部状态由对象是否存在映射为：只有 reservation 是“准备中”；event 已校验是“业务记录已写”；公开快照已校验是“公开快照待确认”；commit 存在是“已完成”；abort 存在是“可重试失败”。这些状态不进入现有业务 API，只用于恢复与审计。

不在失败时删除 reservation 或事件。未提交对象由维护工具列出并诊断；确认无有效 commit 且超过保留期后才可清理，避免网络超时造成误删已写数据。

### 5.4 立即可见性

保存成功响应必须在 commit 写入和回读验证后才返回。读取时先确定最新已提交检查点/事件末端；进程缓存的键包含末端 ID。写入实例主动失效自己的缓存，其他实例若发现新的末端 ID则重载。

这一点依赖 COS 在当前访问方式下的“写后读、写后列举”实际行为。Phase 0 必须用两个独立函数实例做并发和立即读取验证；若 2 秒内不能稳定看到最新提交，本方案不得进入真实数据迁移，转入第 12 节的备用决策。

## 6. 查询、检查点与压缩

对象事件是权威真相，但请求不能每次扫描全部历史：

1. 初始迁移产生 generation 0 完整检查点。
2. 正常读取载入最新已提交检查点，再折叠其后少量已提交事件。
3. 个人列表、审核队列、角色清单和公开文章列表都在检查点中作为可重建索引保存；索引携带相同末端 ID 和哈希。
4. 当待折叠事件超过数量或体积阈值时，仅在一次本来就发生的显式写请求末尾尝试生成新检查点；不得设置定时器或后台轮询。
5. 检查点先压缩、再 AES-256-GCM 加密，写入版本化对象并校验，最后写入 checkpoint commit。旧检查点在独立备份确认前不清理。
6. 压缩完成且独立备份验证后，旧细粒度事件可按保留策略打包成归档对象；稳定主键、最终状态、revision、时间戳、内容哈希和完整审计链必须仍可恢复。

检查点选择算法、分页边界与最大事件尾长度要有固定上限，避免随着投稿积累导致函数超时或请求数无限增长。

一个操作只有在个人草稿/投稿列表、对应审核队列、权限清单和公开快照中所有受影响索引都能重建、末端 ID 一致且内容哈希匹配后才可 commit；任何派生索引都不能单独决定业务真相。

## 7. 公开读取与网址保持

公开快照只含已审核公开字段。发布事件在成功前必须写好新快照、验证其哈希，并让 operation commit 引用该快照版本；发布失败时旧快照继续服务，新文章不可见。

浏览器仍请求原站点和同源 API，不出现 COS 地址。公开快照采用内容哈希版本和长缓存；`lhwiki-api` 在冷启动时载入一次最新已提交版本并使用进程内缓存，普通读者不会让每次页面读取都直达私有工作流存储。函数包内继续保留最后一个已验证公开快照作为故障兜底，但它只可用于读，不能掩盖发布失败。

主站与备用站都从中国大陆网络完成首页、文章、登录、保存、投稿和审核验证；地址栏、API origin、Cookie 域和 CORS 行为必须与切换前一致。

## 8. 安全设计

1. 生产前缀和桶必须验证为私有；浏览器不取得云存储上传凭据，全部私有读写由函数服务端执行。
2. 私有事件和检查点先 gzip，再用 AES-256-GCM 加密；密文保存 `keyId`、随机 nonce 和认证标签。密钥只进入 CloudBase 密钥/环境配置，不写 Git、同步目录、日志或对象元数据。
3. 对象路径的用户/实体部分使用 HMAC，不使用可枚举的原始 ID。公开前缀只保存审核通过的数据。
4. 角色查询缓存按用户与权限 revision 隔离，最长 60 秒；修改角色的实例立即失效。两个冷实例测试撤权传播上限。
5. 审计记录保存操作者授权标识、动作、前后状态、revision、哈希和时间，不重复保存正文或会话密钥。
6. 上传使用 Content-MD5/CRC64 与应用层 SHA-256 双重校验；解密、哈希、关联或 schema 校验任一失败均拒绝读写并告警。

## 9. 数据迁移、切换与零丢失

### 9.1 迁移范围

迁移器从 PostgreSQL 一次性只读导出全部用户/角色、栏目、文章、贡献者、草稿、投稿、教师投稿与补充、审核事件、索引和仍有业务意义的关联状态，不只迁移已发布或待审数据。

### 9.2 顺序

1. 另行授权后创建新鲜 PostgreSQL 备份；把这次访问视为一次计划性数据库激活。
2. 在本机内存中转换和规范化，敏感中间文件不进入仓库或同步目录。
3. 写入全新的隔离前缀，生成 generation 0 检查点和迁移 manifest，不覆盖现有公开快照。
4. 对每类数据核对源/目标数量、稳定 ID、外键、状态、revision、时间戳和规范化内容 SHA-256；任何差异、孤儿或解密失败都会停止切换。
5. 先让候选函数在预发布配置只读新存储并跑完整契约；生产公开读不受影响。
6. 最终切换时短暂冻结私有写入，导出并迁移最后增量，再次核对 manifest，然后仅切换函数内部 store adapter。静态站、网址和 API 路径不变。
7. 受控完成“保存 → 投稿 → 退回 → 重投 → 通过”后解除冻结。

原 PostgreSQL 至少一个完整计费周期保持原样只读。没有恢复演练、哈希对账和用户单独清理授权，不删除任何旧数据。

### 9.3 回滚

配置层保留回滚开关，但不能直接切回陈旧 PostgreSQL。回滚前先把新对象存储末端事件按稳定 ID 幂等回放到 PostgreSQL，在一个计划维护窗口内批量完成并核对数量、状态、末端 ID 与内容哈希；全部一致后才允许切换 adapter。若 PostgreSQL 不可用，继续用新存储提供服务并修复，不能以丢失新投稿为代价回退。

## 10. 备份与生命周期

1. 对象事件、提交和检查点组成在线恢复源；删除操作同样写墓碑事件，不直接抹除历史。
2. 加密本地备份工具按检查点末端 ID 增量下载对象，并生成一个完整恢复 manifest。十次“完整备份”是十个可独立验证的恢复点，不重复下载未改变对象。
3. PostgreSQL 在首个完整周期内继续提供独立旧数据副本。之后是否启用腾讯云低频/归档桶作为第二云端副本需单独授权和定价复核。
4. PostgreSQL 周归档默认关闭；只有用户明确需要第二审计副本时才开启，且本地先判断存在待归档事件，最多每周一次集中访问。
5. 清理任何在线旧事件前，必须已有已验证检查点、独立备份、恢复演练和内容哈希对账；清理操作单独授权并记录 manifest。

若以后启用 PostgreSQL 归档，每批使用稳定 batch ID、连续事件起止 ID、记录数和规范化内容哈希。只有批量写入后从 PostgreSQL 回读并全部吻合，才写入/推进对象存储侧的不可变归档检查点；失败保持原检查点，同一 batch ID 重试不得产生重复行。

脱敏恢复演练必须保留跨用户归属、角色、revision、状态转换、幂等键结构和关联关系，只把学号、姓名及正文替换为不可逆测试值；恢复后运行跨用户隔离、并发保存、重复审核、教师补充、索引重建和公开快照哈希验证。

## 11. Phase 0：当前 CloudBase/COS 能力验证

实现业务存储前，先在现有桶的全新测试前缀运行不含真实数据的最小探针：

1. 确认桶地域、私有 ACL、版本控制关闭状态和函数身份的最小权限。
2. 用当前函数取得上传授权，验证 `x-cos-forbid-overwrite: true`：两个并发请求写同一键必须恰好一个成功，另一个得到可识别冲突。
3. 从两个独立冷函数实例执行 100 轮“写事件 → 写 commit → 立即 GET/LIST → 读取”，P95 不超过 2 秒且不能漏掉已确认提交。
4. 分别在 reservation、事件、快照和 commit 前后注入超时，确认重试不重复提交且旧状态持续可读。
5. 验证私有对象不能通过匿名 URL 读取；日志、错误和上传响应不泄露 token、密钥、原始学号或正文。

探针只允许写测试前缀，完成后保留结果报告；清理测试对象也需明确列出精确前缀。Phase 0 属于云资源操作，实施时仍需单独授权。

## 12. Phase 0 失败时的备用决策

若当前 CloudBase 上传接口不能可靠传递防覆盖语义，或跨实例写后列举不能满足立即可见性，不用“看起来大概可行”的对象锁上线。按以下顺序处理：

1. 先尝试服务端直连同地域 COS 官方 SDK，仍由原 CloudBase 函数代理，前端网址不变；凭据仅授予专用前缀的最小读写权限。
2. 若 COS 官方 SDK 仍不能满足原子占位与 2 秒可见性，再提交新的技术设计，在同一腾讯云国内链路内选支持条件写/事务的请求式服务。
3. Cloudflare D1 只可作为离线灾备，不能因 Phase 0 失败而自动转成在线依赖。
4. 在备用设计重新确认前，维持现有 v0.8.9，不迁数据、不删除 PostgreSQL、不恢复云端自动保存。

## 13. 成本预算

按 2026-09-09 CloudBase 官方资源点单价：云存储读、写请求均为 10 点/万次，容量为 4.54 点/GB/天；资源点换算为 1000 点/元。

对需求中的月度基准，新增工作流存储预算如下：

| 项目 | 保守用量 | 资源点 |
|---|---:|---:|
| 私有在线物理数据（事件、去重正文块、检查点与保留快照合计） | 不超过 1GB × 30 天 | 136.2 |
| 10,000 次逻辑私有读取 | 最多 20,000 次云存储读取 | 20 |
| 3,000 次业务写及多实体 reservation/event/commit/blob | 最多 30,000 次云存储写入 | 30 |
| 1,000 次快照、检查点、冷启动载入与重试余量 | 最多 10,000 次云存储读写 | 10 |
| 合计 | | **196.2** |

十个完整备份采用本机增量对象缓存和十份恢复 manifest，不重复占用 CloudBase 在线容量。100,000 次公开页面读取继续走既有静态/CDN/函数缓存链路，不逐次读取私有对象存储；设计通过指标强制“公开请求不会逐次读取 COS”，冷启动和发布后的快照载入包含在表中 10,000 次余量内。相应 HTTP 网关、函数与静态流量属于现有网站基线，实施前后用同一负载做差分验证。

预算设置两个阻断条件：

- 活跃在线全部对象（含历史事件、正文块、检查点和保留快照）实占超过 1GB，或月预测云存储请求超过 60,000 次时，暂停切换并重新估算；
- 新存储月度预测超过 200 点时，不得上线，必须先压缩/合并检查点或经用户另行同意改方案。

该预算不把 PostgreSQL 周归档计入常态；默认关闭归档可避免约 85.5 点级别的计划激活。迁移备份只发生一次并单独记入本周期切换预算。按用户给出的约 1000 点当前基线，即使保守计入一次约 85.5 点迁移激活、完整月 196.2 点新存储和 300 点（10 点/日）现有运行健康预算，周期末约 1581.7 点，低于 2100 点目标并远离 3000 点硬上限；正式判断以实际剩余天数按比例折算，而不是把完整月费用重复计入。

## 14. 代码边界

建议新增：

- `cloudbase/functions/lhwiki-api/workflow-service.cjs`：领域状态机与复合操作。
- `cloudbase/functions/lhwiki-api/cos-workflow-store.cjs`：私有对象、条件创建、列举、校验和缓存。
- `cloudbase/functions/lhwiki-api/workflow-crypto.cjs`：压缩、AES-GCM、HMAC 与密钥轮换。
- `cloudbase/functions/lhwiki-api/workflow-schema.cjs`：事件、提交、检查点 schema。
- `cloudbase/maintenance/`：迁移、对账、归档、恢复；不进入正常函数包。
- `test/workflow-contract/`：旧 API 契约、并发、幂等、失败注入、双实例权限测试。

`server.js` 只装配 WorkflowService，不再导入 `pg-store.cjs`。现有 `pg-store.cjs` 保留给维护工具，不能被复制进正常部署包。前端仅增加幂等键生成/复用和明确失败提示，不改页面布局或操作流程。

附录 A 的每一个现有读取和写入路径继续由 `server.js` 接收，再调用 WorkflowService 的领域操作；请求业务字段、成功响应主要字段以及 400/401/403/404/409/429 语义由同一套契约夹具锁定。不得让页面知道对象键、blob、event、checkpoint 或迁移状态。

## 15. 验收门槛

### 15.1 本地

- 固化附录 A 全部 API 的现有请求/响应/错误契约。
- fake 对象存储通过同 revision 并发、重复幂等键、不同正文同键、两审核者竞争、双实例撤权、全部中断点恢复、坏密文/坏哈希和索引重建测试。
- 生产式入口的模块加载钩子证明 `pg-store.cjs` 从未加载；网络拦截证明 `/v1/rdb/rest/` 为 0 次。
- 迁移夹具逐类型完成数量、ID、关系、状态、revision、时间戳和内容哈希对账。

### 15.2 隔离云前缀

- Phase 0 全部通过。
- 连续 20 次普通读取 P95 ≤ 800ms，普通写入 P95 ≤ 2s，无请求超过 8s后仍显示成功。
- 两个真实冷实例完成两位用户同 revision 并发保存、重复投稿、审核退回后重投、两名审核者并发处理、审核通过与发布、教师投稿/补充、角色授予与撤销、快照写入中断、超时重试和恢复演练。
- 匿名访问私有对象失败，公开快照不含私有字段。

### 15.3 生产切换

- 切换前新鲜备份和全量迁移 manifest 通过。
- 两个原网址和同源 API 均未变化，并从中国大陆网络完成关键流程。
- 至少 24 小时受控验证中完成至少 10 次私有读取、5 次手动保存和一组“投稿 → 退回修改 → 重投 → 通过”；用请求时间与 operationId 对齐 CLS，公开读、登录、保存、投稿、审核、发布对应的 PostgreSQL 外部访问桶均为 0。
- 日增资源点不超过 10 点；预测周期末不超过 2100 点。若达到需求中的告警或硬边界，停止非必要维护并回滚/修复。

## 16. 实施顺序与授权边界

设计确认后再编写任务清单；任务清单确认后才开始实现。实现顺序建议为：

1. 契约夹具与 fake 存储；
2. Phase 0 探针（单独授权）；
3. 领域状态机和 COS store；
4. 前端幂等键与完整测试；
5. 脱敏迁移/恢复演练；
6. 真实备份和迁移（单独授权）；
7. 函数部署、静态资源按需部署、24 小时观察（单独授权）。

任何创建资源、修改 ACL/密钥、读取真实生产数据、部署、迁移或清理都不由本设计确认自动授权。
