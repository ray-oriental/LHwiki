# 资源唤醒治理设计

## 证据

- CloudBase 共享 PostgreSQL 只要在一个五分钟周期内发生访问或内部处理，就按 `5 分钟 × 0.5 核` 计费；按 342 点/核时计算，单个最小计费桶约 14.25 点。
- 2026-09-08 的用量截图显示 PostgreSQL CPU 已累计 2.16 核时，名义成本约 738.72 点；该量级不能由“每天零点几分”的旧阈值解释。
- 代码审计确认：旧登录路径会在函数进程首次处理任意有效学号时扫描权限用户；前端每次启动还会请求 `/api/session`，已带特权声明的会话会再次读取用户表。自动扫描或普通页面恢复因此可能把数据库唤醒分散到多个五分钟计费桶。
- 公开快照、普通健康检查、本机自动保存和手动云端写入边界已经存在；本轮重点是消除登录与会话恢复的隐式数据库访问，不削减投稿、审核或权限功能。

## 方案

- 浏览器草稿管理器保留 220ms 本机合并写入，移除所有云端自动/尾随/失败重试状态；客户端协议升至 v4。
- 首次手动保存由单个 POST 完成；同键云端草稿内容相同则复用，不同则返回 409 冲突，只有携带已知 revision 的 PUT 可以更新，避免用一次请求优化破坏多标签页保护。
- 登录只校验学号格式并签发 HMAC Cookie；普通账号和受保护管理员不查询用户表。已有、同一学号且仍有效的签名会话可保留其显示角色，避免为了登录展示权限而唤醒数据库。
- `/api/session` 只验证 Cookie 的签名、版本、角色与过期时间，不读取数据库。浏览器把非敏感的会话显示信息缓存在本机，公开页面启动不再调用该接口；后端 Cookie 仍是访问控制依据。
- 签名角色不是最终授权。除受保护管理员外，审核者或管理员进入任何私有操作时都查询用户表实时复核；撤权立即影响后端操作，前端在 401/403 后清除本机会话显示缓存。
- 普通写作入口优先从 `localStorage` 恢复新草稿，不预读 `/api/mine`。用户显式进入“我的投稿”时才一次读取草稿、投稿和教师补充，并在当前页面会话内复用；私有写操作会立即清除此缓存。云端深链接在本机无对应内容时仍可按需回源，避免损害跨设备恢复。
- 增加 `/api/mine` 聚合接口，在一次函数执行中并行读取三个列表；保留旧读接口以兼容，但新版前端不再调用。
- 删除前端访问计数队列、计时器和上传函数；后端兼容路由固定返回暂停状态。
- 审核批准或管理员更新公开内容时，在同一次明确数据库操作中生成严格白名单快照并覆盖对象存储固定对象；公开读取不访问 PostgreSQL，失败则回退随函数部署的公开快照。
- 资源监控以 3000 点为硬上限、2100 点为运行目标并保留 900 点安全余量，记录实际周期速度、预测周期总量和 CLS 中不同的 PostgreSQL 五分钟桶。先标注开发/部署活动；安静时段零桶才算符合零隐式唤醒目标。

## 未采用的集中写入方案

- 不在云函数内使用延迟内存队列：函数实例无状态且可随时回收，响应结束后不能可靠保存待写数据。
- 不用高频定时任务强制刷库：定时器本身会制造固定数据库活动窗口，边缘情况下还可能重复触发；对五分钟计费桶而言可能比低频人工操作更贵。
- 不在本轮把私有草稿迁入 PG 模式云存储：官方接口说明对象元数据和权限由 PostgreSQL RLS 在事务中协调，无法据此保证零 PostgreSQL CPU；同时需要新增 Bucket、RLS、并发覆盖与备份恢复边界。
- 当前采用“零隐式访问、显式操作聚集”的方案：浏览与写作留在端侧，公开读取走快照，只有用户明确请求跨设备云备份、正式提交或审核管理时访问 PostgreSQL。相邻操作自然落入同一五分钟桶，不增加人为定时唤醒。

## 发布与回滚

- 无数据库迁移。发布顺序为：新鲜备份 → `lhwiki-api` → 静态前端 → 浅健康检查 → 单次功能冒烟。
- 若安静时段仍出现数据库桶、连续两个监控区间超过 2100 点目标速度，或活跃速度预测周期会超过 3000 点，则重新启用前后端维护常量并只部署函数与静态前端；数据库无需回滚。
