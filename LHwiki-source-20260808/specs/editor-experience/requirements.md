# LHwiki 内容输入体验重构：需求文档

状态：待确认
范围：Web 编辑器、云端草稿、投稿/审核/发布内容结构、文章子目录
非目标：图片、视频、附件、表格、任意 HTML、多人同时协作编辑

## 1. 背景与目标

当前投稿页依赖单个 `contenteditable` 区域和浏览器 `execCommand`，提交时再从 DOM 猜测内容块类型。该方案输入反馈不稳定，刷新无法恢复，标题/列表等结构在审核与发布后可能丢失，也没有长文导航。

本次重构的目标是：让学生不接触 Markdown 或 HTML 等“编码”，直接以接近 Notion 的内容块方式写作；在输入、刷新、断网、跨页面和提交过程中都能明确知道内容是否安全；同一份结构化正文应在编辑、审核、发布和管理员修改后保持一致；含标题的文章应自动生成类似 Word 导航窗格的子目录。

## 2. 用户故事

### 2.1 投稿学生

- 作为学生，我希望点击正文后立即输入，不需要理解任何标记语言。
- 作为学生，我希望用工具栏、斜杠菜单或常用行首快捷写法切换正文、标题、引用和列表。
- 作为学生，我希望每次修改都先在本机恢复缓存中留下副本，并在短暂停顿后自动保存到云端。
- 作为学生，我希望随时看到未保存、保存中、已保存、离线或冲突状态。
- 作为学生，我希望刷新、关闭后重开或切换页面后继续上次草稿。
- 作为学生，我希望投稿成功后，审核者和最终读者看到的标题、层级、引用和列表与我写作时一致。
- 作为学生，我希望在“我的投稿”中管理多份草稿，继续编辑或明确删除，而不是误覆盖。

### 2.2 审核者与管理员

- 作为审核者，我希望预览与最终文章使用同一渲染器，以便所见即所得地判断稿件。
- 作为管理员，我希望修改已发布文章时也使用同一编辑器和自动保存能力，避免刷新丢失。
- 作为管理员，我希望发布旧文章时不必手工迁移，旧格式仍能正常阅读。

### 2.3 读者

- 作为读者，我希望长文自动出现可点击的二级子目录，并能看到当前阅读位置。
- 作为手机读者，我希望目录可折叠，不遮挡正文。

## 3. 功能需求与验收标准

### R1. 无编码的内容块编辑器

1. 编辑器必须以独立内容块组织正文，首版支持：正文、二级标题、三级标题、引用、无序列表、有序列表。
2. 每个块必须具有稳定标识、类型和纯文本内容；系统不得保存或渲染用户输入的原始 HTML。
3. 当用户按 Enter 时，编辑器应在光标处拆分当前块；当空块按 Backspace 时，应合并或退回正文类型，不丢失相邻内容。
4. 编辑器应支持块类型工具栏和 `/` 斜杠菜单；输入 `## `、`### `、`> `、`- `、`1. ` 后应可转换为对应块，但这些符号不得出现在最终正文中。
5. 从网页或文字处理软件粘贴时，系统应清除危险 HTML 和媒体，仅保留纯文本、换行及可可靠识别的段落结构。
6. 编辑器应支持 Ctrl/Cmd+S 手动触发保存，并显示字数与内容块数量。
7. 编辑器应提供键盘可达的按钮、可见焦点、ARIA 标签和保存状态播报。

### R2. 本机恢复与实时云端保存

1. 当正文或元数据变化时，系统应在 300ms 内更新本机恢复缓存。
2. 用户停止输入约 1.2 秒后，系统应自动向云端保存草稿；连续输入期间不得按每次按键请求服务器。
3. 页面必须明确展示以下互斥状态：未保存、正在保存、已保存（含时间）、离线保存在本机、保存冲突、保存失败可重试。
4. 刷新页面或重新进入投稿页时，系统应恢复最近草稿；云端和本机均存在时，应比较更新时间/版本，不得静默用旧版本覆盖新版本。
5. 网络中断时，编辑必须继续工作并保存在本机；网络恢复后应自动重试云端保存。
6. 多标签页或多设备编辑同一草稿时，服务端应使用递增版本号做乐观并发控制；版本不匹配必须返回冲突，不得后写静默覆盖先写。
7. 登出、草稿删除或投稿成功后应清除对应本机恢复缓存；已保存的云端草稿在正常登出后保留。
8. 用户关闭页面前若仍有未发送修改，系统应尽力执行一次轻量保存，并保留本机副本作为兜底。

### R3. 云端草稿生命周期

1. 草稿必须存放在独立 `drafts` 数据表中，不得进入审核队列。
2. 草稿必须绑定当前登录身份；普通用户只能读取、修改和删除自己的草稿。
3. 草稿应支持三种目标：新投稿、修改尚可编辑的投稿、管理员修改已发布文章。
4. “我的投稿”必须单独展示草稿，包含标题占位、最后保存时间、继续编辑和删除操作。
5. 删除草稿必须二次确认；投稿成功后，服务端必须在创建/更新投稿成功之后再删除对应草稿。
6. 草稿允许字段暂时为空；真正投稿时继续执行现有标题、摘要、正文、栏目和署名校验。
7. 草稿接口应限制正文体积、内容块数量和请求频率，并沿用现有会话、CSRF、来源校验与安全响应头。

### R4. 内容结构完整保真

1. 同一份结构化正文必须由编辑页、审核页、发布页和管理员编辑页共用解析与渲染规则。
2. 发布/审核流程不得把二级标题、三级标题、引用和列表降级为普通段落。
3. 旧数据中的 `heading` 必须向后兼容为二级标题；新数据可增加三级标题类型，但不得破坏旧文章。
4. 服务端必须重新校验块标识、类型和文本长度，并丢弃客户端未声明或不安全字段。
5. 任意用户文本必须通过文本节点渲染或等价转义，禁止脚本、事件属性和 `javascript:` 内容进入页面。

### R5. 文章子目录

1. 含至少两个标题块的文章必须自动生成“本文目录”；标题不足时不显示空目录。
2. 目录必须按二级/三级标题形成两级层次，三级标题视觉缩进。
3. 点击目录项应平滑滚动至正文标题；标题锚点应稳定且同名标题不得冲突。
4. 桌面端目录应位于文章右侧并在阅读时保持可见；移动端应折叠为正文前的“本文目录”。
5. 页面滚动时，目录应高亮当前章节；禁用动画偏好的用户不得被强制平滑滚动。
6. 目录必须可用键盘操作，并在没有 JavaScript 增强时仍能通过普通锚点跳转。

### R6. 易用性与反馈

1. 首次进入编辑器时应以一行简短提示说明 Enter、`/` 和自动保存，不展示技术术语。
2. 空段落应有克制的占位提示；工具栏不得长期占据大面积正文空间。
3. 保存失败不得阻止继续输入，也不得只用红色表示错误；应提供文字说明和“重试”。
4. 投稿前应显示结构化预览；预览与审核/发布应使用同一渲染器。
5. 页面离开时，仅在本机与云端均未可靠保存的极端情况下弹出离开确认，避免频繁打断。

## 4. 数据与接口约束

- 新增 `drafts` 表，至少包含：`id`、`student_id`、`draft_key`、`target_type`、`target_id`、各投稿字段、`body_json`、`revision`、`created_at`、`updated_at`。
- `(student_id, draft_key)` 必须唯一；`revision` 每次成功保存递增。
- 建议接口：`GET /api/drafts/mine`、`POST /api/drafts`、`PUT /api/drafts/:id`、`DELETE /api/drafts/:id`、`POST /api/drafts/:id/submit`。
- 保存接口必须接收客户端期望版本；冲突返回 HTTP 409 和服务端最新元数据。
- 投稿提交应由服务端完成“校验内容 -> 创建/更新投稿 -> 删除草稿”的有序流程；若中途失败，草稿不得丢失。

## 5. 非功能需求

- 不引入境外 CDN、字体或运行时资源，保障中国大陆访问路径不增加外部依赖。
- 自动保存请求应使用防抖、串行队列和指数退避；单个用户持续正常写作不得触发现有滥用防护。
- 编辑器在常见桌面浏览器与移动浏览器上可用；窄屏不得出现横向滚动。
- 文章和草稿继续受现有备份流程覆盖；新增表必须加入备份、恢复与校验清单。
- 数据迁移必须可重复执行，旧文章无需一次性重写。

## 6. 完整验收流程

1. 学号登录后新建草稿，输入不同块类型，等待显示“已保存”。
2. 刷新与关闭重开，确认标题、署名、栏目、正文类型和光标附近内容均恢复。
3. 断网编辑后刷新同页，确认本机恢复；恢复网络后确认云端版本递增。
4. 在两个标签页编辑同一草稿，确认旧标签保存得到冲突提示且无静默覆盖。
5. 投稿并进入审核，确认预览结构不变；审核通过后文章结构仍不变。
6. 打开发布文章，确认目录层级、跳转、当前章节高亮与移动端折叠均正常。
7. 管理员修改已发布文章，刷新编辑页再继续，保存发布后修改持久化。
8. 打开历史文章，确认旧 `heading`、列表、引用和日期展示无回归。
9. 尝试脚本、超长文本、非法块类型、越权草稿 ID 和快速重复保存，确认均被安全拒绝或限流。

## 7. 待确认边界

- 首版结构化格式仅包含标题、引用和列表，不加入粗体、斜体、链接、代码块或媒体；这些可在正文模型稳定后作为第二阶段扩展。
- 首版不做多人实时共同编辑；通过版本冲突保护内容。
- 审核通过后普通投稿者仍不能直接改线上文章；管理员可编辑，其他修改继续走审核流程。
